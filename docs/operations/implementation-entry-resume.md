# ACE SDLC — harness-neutral entry and resume at any stage

**Scope:** this is a repository-owned instruction contract for **any compatible coding harness/agent** (Hermes currently, but not a Hermes-specific adapter): one agent at a time, no background runner or second orchestration engine. Route the latest owner instruction **before** selecting the first SDLC step. The owner asks for an operation, not necessarily an entire fresh R→S→A→P→X→I→V journey. Read root `AGENTS.md`, applicable accepted ADR/OpenSpec and `.agents/skills/ace-sdlc/SKILL.md`. A harness must actually discover and apply the project skills; their presence alone does not demonstrate host execution.

## Intent + project state → selected stage

| Stage | Owner intent examples | Reuse existing inputs; stage-specific output |
| --- | --- | --- |
| **R — Research** | "исследуй", "research this", "изучи текущую реализацию" | Source/branch and existing source facts → a focused fact-only research memo; no S/A/P by default |
| **S — Requirements** | "подготовь требования", "write the spec", "сформируй OpenSpec" | Existing valid R evidence + current source → update **the same** `proposal.md` and `specs/**/spec.md`; do not automatically redesign or slice |
| **A — Architecture** | "спроектируй", "architecture", "доработай design" | Existing S/specs and accepted ADRs → update **the same** `design.md` / decision crosswalk; not Research or ticket generation by default |
| **P — To-tickets** | "разбей на чанки", "split into tasks", "составь DAG" | Existing reviewable design + specs → update canonical `tasks.md`; no unnecessary architecture redesign |
| **X — Detailed phases / synthesis** | "детализируй чанки", "write phase briefs", "синтезируй планы" | Existing canonical tasks, design, specs → update only linked `phases/<ID>.md` and required synthesis inputs; do not repeat P/A/R unless inputs actually changed |
| **I — Implement** | "имплементируй", "реализуй C01", "apply the approved plan" | Existing `tasks.md`, exact phase brief, actual G02/dependency permission → RED/GREEN and one approved phase PR; no planning rerun |
| **V — Verify/review** | "проверь", "review this PR", "прими результат", "verify" | Existing code/PR, acceptance and retained evidence → scoped build/architecture/security/plan review, provider E2E where applicable; do not implement or replan automatically |
| **Resume any stage** | "продолжай", "continue", "resume" | Restore the **verified last active R/S/A/P/X/I/V stage**, its branch/PR/input hashes and incomplete work; do not assume "continue" means I |
| **Start from scratch** | Explicit "redo the whole SDLC" or genuinely new capability with no usable inputs | Start at R, then only proceed across stages authorized by the request and existing G02 gates |

Interpret examples semantically, **not via string matching alone**. An explicit stage/phase request takes precedence over a stale session checkpoint; no automatic change in task scope. A fresh harness session does **not** mean that R is required again.

## Universal admission procedure (all R/S/A/P/X/I/V)

1. **Choose entry:** from the latest explicit owner request, then current conversation/task ID, active worktree/PR and checkpoint. Explicit stage or phase ID wins; "continue" selects the last verified in-progress stage; otherwise infer only an unambiguous owning stage from the requested artifact/action. If multiple changes remain plausible, identify the ambiguity instead of silently creating new OpenSpec work.
2. **Read authority and actual state:** root/nested AGENTS; accepted ADR and current OpenSpec; remote/main or stacked parent branch HEAD; current worktree, open/merged PRs and actual commits; only relevant upstream artifacts. Check `openspec list --json` and `openspec status --change <change-id> --json` where applicable. Check `openspec instructions <stage-artifact> --change <change-id> --json` for planning artifacts, or `openspec instructions apply --change <change-id> --json` for I; obey the selected OpenSpec store and never auto-initialize a new root.
3. **Validate stage-specific prerequisites, not every earlier stage:** R needs source identity; S needs sufficient verified source facts/requirements authority; A needs valid requirements/specs; P needs a reviewable design; X needs a canonical DAG and valid design/specs; I needs the selected phase, completed dependencies, current design/spec fingerprints and **real G02 owner decision for material T2**; V needs the actual deliverable, applicable acceptance and observed evidence. Earlier existing stages are **reused** rather than re-executed. For partial R/S gaps, gather only necessary missing evidence and return to the requested stage.
4. **Scope freshness:** compare actual source, Git blob IDs/spec hashes, acceptance ownership and parent stage PR against the consumed artifacts. If a *specific* prior input is missing or materially STALE, repair **only its owning stage and dependent artifacts** and then return to the requested stage; do not rebuild the complete R→X pipeline. Planning may remain PROVISIONAL until owner choices are decided. The read-only `check:ace-phase-plan` is for X/I phase briefs, not a prerequisite to R/S/A.
5. **Select the existing canonical skill/command:** R → `research_codebase.md`; S → `ace-sdd-prepare` Requirements/`to-spec`; A → `ace-architecture-design`; P → `ace-to-tickets`; X → `ace-phase-plan` and **`ace-plan-refinement` only when new/affected material T2 dual-plan synthesis is actually required**; I → `openspec-apply-change` constrained by ACE to one phase + `implement_backend.md`; V → `openspec-verify-change` and relevant review checks. Do not invoke unrelated skills simply because they appear earlier in the diagram.
6. **Preflight and authorization:** use the existing read-only `npm run sdlc:preflight -- --tier <T0|T1|T2> --stage <research|design|plan|implement|review> --json`; map R → research, S/A → design, P/X → plan, I → implement, V → review. This diagnostic does not certify stage entry, owner G02 or CI. Use `worktree:preflight` and isolated branch/PR before writes. G02 is **not a blanket prerequisite to R/S/A/P/X**: a provisional design/plan can be prepared, but dependent T2 implementation is blocked until explicitly approved. Missing provider/model/data-class authorization blocks its corresponding external action, not ordinary offline planning.
7. **Act only within selected scope, then resume safely:** commit/review the selected stage; don't duplicate a completed PR. Record stage, task/change/phase, branch/base/head, input blobs, checkpoints, owner decisions, gate verdicts and exact next action. On resume compare those records with current code/Git/OpenSpec; replay neither external side effects nor already-complete work without idempotency evidence.

## Result vocabulary

- **ENTER_STAGE(R|S|A|P|X|I|V)**: stage chosen from explicit intent and current valid inputs; perform only its work.
- **RESUME_STAGE(R|S|A|P|X|I|V)**: last verified active stage and worktree/PR reused; continue unfinished portion.
- **REPAIR_OWNING_STAGE(stage)**: a specific upstream dependency is stale or incomplete; minimal correction, refresh affected descendants, then return to requested stage.
- **BLOCKED_INPUT / BLOCKED_G02 / BLOCKED_DEPENDENCY / BLOCKED_EGRESS / BLOCKED_AMBIGUOUS**: report exact blocker at the selected stage; no fabricated PASS and no fallback to full Research.
- **START_NEW_PIPELINE**: explicitly new end-to-end task or no usable existing artifacts after inspecting actual state.

**Do not infer state from a checkpoint alone.** No new durable phase tracker or parallel OpenSpec change for the same work. The existing `tasks.md` is the one acceptance ledger. Stage-specific PRs stack only when producing *new* stages; restarting an existing stage reuses its branch/PR. Static docs/tests are not live proof that Hermes or another harness really chose the correct entry.

## Implementation-specific admission (additional gates for I)

### Direct I-stage admission (read-only first; no speculative replanning)

1. **Resolve the owner-selected change and phase (after universal stage routing).** Prefer explicit change/phase ID, then the active PR/worktree and existing checkpoint, then the only unambiguous current OpenSpec change. If multiple plausible plans remain, ask only which one; do not invent a new change. Discover state via `openspec list --json`, `openspec status --change <change-id> --json` and `openspec instructions apply --change <change-id> --json` using the project's declared OpenSpec store where applicable. Follow its `contextFiles` and blocked states; never create new artifacts merely to satisfy a router.
2. **Use the single canonical plan.** Read `openspec/changes/<change-id>/tasks.md`, accepted specs, `design.md` and the **entire** `phases/<phase-id>.md`. Pick the explicitly named phase; otherwise resume the one genuinely IN-PROGRESS on the live branch/PR; otherwise take the first **dependency-ready, unimplemented** phase in the canonical DAG. Check source/PR reality before trusting a checkbox; a green stale PR or unchecked task is not proof of work remaining. If all phases are implemented, route to V rather than rebuilding the plan.
3. **Freshness is scoped.** Compare the phase's design Git blob, sorted-spec fingerprint, AC ownership, dependency DAG and exact source interfaces against **current** checkout/branch/parent PR. Run `npm run check:ace-phase-plan -- --change <change-id> --phase <phase-id> --json`. Its `READY_FOR_PHASE_REVIEW` is a structural signal, **not** approval. Check changed source/contracts and overlapping PRs only as needed. If an input is STALE, reconcile the affected owning S/A/P/X artifact and descendants; never silently rewrite the entire plan or label it approved.
4. **Authorize safely.** Read applicable accepted ADR/OpenSpec and *actual* G02 owner decision/reference for material T2; a `design.md`, G02 table, `--g02` file or latest "implement" instruction **does not by itself approve** an unresolved architectural decision. A missing/denied provider, model, data-class or paid external-egress permission blocks only the dependent external action. With no owner G02 for a T2 implementation, report **BLOCKED_G02** and the exact decision needed; **do not fall back to Research** or start modifying product code.
5. **Enter implementation directly.** On a safe isolated worktree/PR run `npm run worktree:preflight -- --task-id <task-id> --json` and the existing read-only `npm run sdlc:preflight -- --tier T2 --stage implement --task-id <task-id> --plan openspec/changes/<change-id>/tasks.md --g02 openspec/changes/<change-id>/design.md --json` (T1: omit `--g02` and use `--tier T1`). Verify the owner approval *separately*. A `REVIEW_REQUIRED` preflight is not an implicit STOP if the agent can independently show the required approval, nor is it an automatic PASS. Follow `openspec-apply-change` instructions **constrained to this one ACE phase** and the **complete** `docs/research/sdlc/source/commands/implement_backend.md`; implement actual RED → GREEN → BUILD/ARCH/SEC/PLAN reviews → bounded `verify:pr` → PR. Do not let generic OpenSpec "loop until done" override ACE's one-phase limit.
6. **Resume I, don't reset.** Reuse the existing branch/worktree and open PR if applicable; preserve dirty/unrelated changes and any previously committed RED/GREEN evidence. Re-read the exact HEAD, checkpoint, source and current plan. Idempotently continue remaining tasks. Never discard/reapply an external side effect or use a stale checkpoint as authority.



### Example — existing G11 phases

For an owner command "Implement C01 from `openspec/changes/013-gateway-g11-production-acceptance/tasks.md`", enter **I / C01**, inspect its current plan and relevant source, and validate G02/permissions. Do **not** begin R/S/A/P/X merely because the normal diagram starts at Research. If G02 is still `REVIEW_REQUIRED`, stop as **BLOCKED_G02**; report the unresolved owner decision rather than writing code or regenerating the eight phase plans. For "review G11 design" enter A or V according to whether the owner asked to **change** or **review** the design; for "continue C03 planning" resume X, not I.
